## Investigation report

The shell mismatch is real, but it is only one contributor. Several other issues can independently cause excessive tool calls, unintelligible output, or recursion.

### 1. Shell selection is not end-to-end

The extension now accepts `cmd`, `powershell`, and `bash`, but the backend’s `shell_exec` skill accepts the `shell` argument and then ignores it when running backend-side commands.

In `shell_exec.py`, `shell` is accepted, but execution delegates to `execute_sandboxed(...)` without passing shell selection. Therefore:

- Client-delegated shell commands can use the requested shell.
- Backend-executed shell commands cannot.
- The model may request PowerShell while the backend sandbox still uses its own default shell.

This creates inconsistent behavior between `client_type="vscode"` and other clients.

### 2. `default` shell behavior is ambiguous

The extension resolves `default` to:

- PowerShell on Windows
- Bash on Linux/macOS

But the visible terminal may have previously been created as CMD. The model receives a list of available shells, but not necessarily the currently active shell session. This can lead to commands being generated for one shell while the persistent terminal is still another.

The shell identity should be explicit in every command lifecycle:

```text
requested shell
resolved shell
actual executable
working directory
```

### 3. Shell switching can orphan a pending command

In `ensureShellSession`, switching shells kills the existing process before `executeCommand()` checks whether `_pendingShellCommand` is active.

Current order:

1. Resolve requested shell.
2. Kill existing shell if shell type differs.
3. Later check `_pendingShellCommand`.

If a command is running and the agent requests a different shell, the process can be killed while the pending Promise remains unresolved until timeout. This can make the backend appear stuck and may trigger retries or repeated tool calls.

### 4. Persistent interactive shell output is inherently noisy

The extension uses interactive processes:

- CMD: `/Q /K`
- PowerShell: `-NoExit -Command -`
- Bash: interactive mode

As a result, output can contain:

- Prompt text
- Command echo
- Previous command output
- Shell startup noise
- Marker output
- Partial lines split across events

The parser accumulates raw stdout and only removes the marker line. It does not remove the command prompt or echoed command. Therefore the model receives output such as:

```text
c:\workspace>dir
...
c:\workspace>
```

This explains the “unintelligible” trace even when the command succeeds.

A better design would use a non-interactive process per tool call, or maintain a shell-specific prompt protocol and strip prompt/echo lines explicitly.

### 5. The command marker protocol is shell-specific and fragile

The extension uses different markers:

- CMD: `echo MARKER %ERRORLEVEL%`
- PowerShell: `Write-Output "MARKER $LASTEXITCODE"`
- Bash: `echo MARKER:$?`

Potential problems:

- `$LASTEXITCODE` can be stale or empty for some PowerShell commands.
- PowerShell native command failures may not produce the expected exit semantics unless `$ErrorActionPreference` and native error handling are configured.
- Bash startup/profile behavior differs by platform.
- Marker text could theoretically appear in command output.
- The parser identifies a line by substring rather than validating that it is the final marker generated by the current command.

A malformed or missing marker causes a 60-second timeout, which can prompt backend retries.

### 6. One global `_pendingShellCommand` serializes all shell operations

The extension only supports one pending shell command:

```ts
private _pendingShellCommand?: ...
```

If the agent emits multiple shell calls, the second receives:

```text
Error: A shell command is already running.
```

This is especially relevant because the backend can issue multiple tool calls during graph execution. The model may interpret this as a failed environment operation and retry the same command.

Parallel shell execution is unsafe with one persistent shell, but the system currently exposes no explicit queue or backpressure mechanism.

### 7. Successful tool results intentionally re-enter the model

The graph routes:

```text
reason → execute_tool → verification → guard → reason
```

This is expected for agentic behavior, but there is no strong “successful read/list operation” completion rule. After a successful `workspace_reader` or `shell_exec`, the model is simply asked to reason again and may call the same tool.

The duplicate-call guard only stops after repeated identical calls. It does not prevent the first unnecessary repetition.

This is likely the main reason the agent “over-does” tools after the shell starts working.

### 8. Tool-call fingerprints are not persisted across requests

The repeated-call detection uses state-local history:

- `recent_actions_fingerprint`
- recent messages since the current user message

A new user turn or retry can reset the relevant state. Therefore a sequence like:

```text
workspace_reader
assistant explanation
workspace_reader
assistant explanation
workspace_reader
```

may not always be recognized as the same operational loop, depending on how history is reconstructed and summarized.

### 9. Tool calls are semantically under-specified

The backend shell schema describes only:

```text
command
cwd
shell
```

It does not require the model to state:

- Why the command is needed.
- Whether the command is read-only or mutating.
- Whether the result is sufficient to answer the user.
- Whether the command is client-side or backend-side.
- Whether the shell is selected deliberately.

This encourages the model to issue generic discovery commands repeatedly.

Similarly, `workspace_reader` accepts `action`, `path`, and `recursive`, but does not communicate a strong “one authoritative client workspace” contract through its tool schema itself.

### 10. Backend and client shell tools share the same name

Both environments expose `shell_exec`, but they have different semantics:

- Backend shell: backend filesystem/sandbox.
- Client shell: IDE workspace terminal.

The model sees one logical tool name, while execution location depends on client delegation. This is a major source of conceptual confusion.

A safer protocol would distinguish them explicitly, for example:

- `client_shell_exec`
- `backend_shell_exec`

or include an immutable execution target in the tool metadata.

### 11. Backend workspace operations still have a separate root

The backend workspace reader and shell tools resolve against:

- `PROJECT_ROOT`, or
- conversation scratch space

The IDE tools resolve against `vscode.workspace.workspaceFolders[0]`.

This is now protected better for VS Code delegation, but the underlying dual-root architecture remains. Any delegation failure, missing WebSocket, unsupported client type, or tool capability mismatch can still cause backend execution against the wrong filesystem.

### 12. WebSocket tool-response handling is vulnerable to stale messages

Tool responses are routed by `tool_id`, which is correct, but there is no explicit request-generation/session identifier. If a connection is interrupted and reconnects while a tool is pending, a late response could be:

- dropped as an unknown tool ID,
- routed to a reused ID,
- or leave the original graph waiting until timeout.

The WebSocket client reconnects automatically, but it does not appear to restore or reconcile pending tool calls.

### 13. Cancellation does not fully synchronize shell state

Cancelling generation kills the shell process and clears `_pendingShellCommand`, but the backend may still be awaiting a client tool response. The client and backend can therefore disagree about whether a tool is active.

That can lead to:

- late tool responses,
- unknown tool IDs,
- repeated agent attempts,
- stale shell state after cancellation.

### 14. The model is not told whether a shell command failed because of syntax or environment

The extension returns combined text:

```text
Stdout:
...
Stderr:
...
Exit Code: ...
```

The model has to infer whether:

- the shell syntax was wrong,
- the executable was missing,
- the command ran in the wrong directory,
- the command was denied,
- the command timed out,
- the shell process died.

Structured result metadata would be much more reliable:

```json
{
  "success": false,
  "shell": "cmd",
  "cwd": "...",
  "exit_code": 9009,
  "stdout": "...",
  "stderr": "'ls' is not recognized..."
}
```

### 15. Verification can generate additional shell calls

The verification node automatically creates a `shell_exec` call after file writes. This is useful, but it can compound loops:

```text
workspace_writer
verification shell_exec
verification result
reason
another workspace_writer
another verification shell_exec
```

There is no clear cap on automatic verification calls per user turn, and the verifier may use a different cwd/root convention than the original operation.

## Most likely current failure chain

The behavior you observed is probably a combination of:

1. The model chooses a shell command.
2. The extension runs it through a persistent interactive shell.
3. Prompt and command echo contaminate the returned output.
4. The model cannot clearly determine whether the command succeeded.
5. The graph routes back to `reason` after every tool result.
6. The model repeats discovery or shell commands.
7. The guard eventually detects identical calls, but only after several unnecessary iterations.
8. If a marker is missed or the shell is switched during execution, the command waits or times out, causing further retries.

## Highest-priority design changes

1. **Separate client and backend tools semantically.**
2. **Return structured shell results**, not only formatted text.
3. **Use non-interactive process execution per command**, or implement robust shell-specific prompt isolation.
4. **Make shell selection explicit in the tool call and result.**
5. **Prevent shell switching while a command is pending.**
6. **Add a successful-read completion policy** so one successful workspace listing/read does not automatically trigger another identical call.
7. **Add a per-request tool budget and duplicate-call budget.**
8. **Carry tool request IDs across reconnects and cancellation.**
9. **Make backend shell execution honor the requested `shell` field.**
10. **Add tests for CMD, PowerShell, Bash, missing shell, command failure, timeout, cancellation, shell switching, and repeated tool calls.**
